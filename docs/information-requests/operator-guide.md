# Information Requests operator guide

This guide is for the people who run DocuHyphen: platform administrators, support, and whoever
deploys it. It covers configuration, commercial states, quotas, abuse controls, workers, and support
diagnostics. For failure recovery, see `recovery-runbook.md`. For endpoints, see `api-reference.md`.

## Commercial and operational states

The owner of a request's Exchange (an organization or a person) provides the plan. Parties who
respond or review never need a plan of their own.

| State                                              | Effect                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | How it is set                                           |
|----------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------|
| Enforcement mode `ENFORCE`                         | Plan refusals are raised.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | `app.subscription.enforcement.mode` (default `ENFORCE`) |
| Enforcement mode `REPORT_ONLY`                     | Refusals are logged (`event=subscription_decision outcome=WOULD_DENY`) and allowed. Grants issued in this mode carry no allowances.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | same key                                                |
| Enforcement mode `OFF`                             | Plan checks are skipped. Grants carry no allowances.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | same key                                                |
| Lapse: trial ended, past due after grace, canceled | New requests, drafts, follow-ups, and Template changes are refused. Issued requests continue under their execution grant.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | subscription status                                     |
| Operational suspension                             | Nothing on the owner's requests can change, whatever the enforcement mode, scheduled work included: clock reminders, overdue marks and notices, escalations, and expiry wait (see Workers), queued notices and their retries are skipped as `OPERATIONALLY_SUSPENDED`, no clock can be started, paused, resumed, or extended, no access link can be issued, resent, or replaced, and no participant can link an account (`403`, `SUBSCRIPTION_SUSPENDED`). Access can still be reduced: revoking a party, an access link, delegated authority, or an accepted fact stays possible. Everything stays readable and exportable.                      | subscription status `SUSPENDED`                         |
| Execution grant revocation                         | One request stops for good: answers, reviews, imported values, generated outputs, fact promotion, business decisions, issuing, resending, or replacing an access link, and starting or resuming a clock are refused. Removing a party, revoking an access link or a fact, and pausing or extending a clock stay possible, and so does changing the completion gate when the grant lists `CANCEL`. Its clocks record no further reminder, overdue mark, escalation, or expiry, and its queued notices are skipped as `EXECUTION_GRANT_REVOKED`. It stays readable and exportable. The database writes a revocation once and refuses to rewrite it. | platform action on the grant                            |
| Action not in the grant                            | A change whose continuation action the request's frozen grant does not list is refused (`INFORMATION_REQUEST_CONTINUATION_NOT_GRANTED`, `409`). Grants issued today list every action. Typed Field answers follow the grant when it includes typed Fields, otherwise the owner's live plan. A grant without `SEND_REMINDER` also holds its request's scheduled clock points and skips its reminder and overdue notices as `CONTINUATION_NOT_GRANTED`.                                                                                                                                                                                             | the grant frozen at issue                               |
| Trusted relationship suspended                     | New trusted assignments, and issuing a request with a party bound to that relationship, are refused (`INFORMATION_REQUEST_TRUST_SUSPENDED`; a recipient that can no longer be assigned is `INFORMATION_REQUEST_TRUSTED_RECIPIENT_UNAVAILABLE`). Parties on issued requests keep working. A member who joins a trusted group while its relationship is suspended or no longer eligible is held back: they cannot act for the group party or reach the request or its Exchange through the group until trust is eligible again, and the members reconciled when the last suspension clears gain access then.                                        | Trusted Organizations                                   |

Reads are never hidden by any of these. Each request projection states an execution standing:
`ACTIVE`, `NEW_WORK_UNAVAILABLE`, `CONTINUING_AFTER_LAPSE`, `OPERATIONALLY_SUSPENDED`, or
`EXECUTION_GRANT_REVOKED`. Only callers who manage the request see the owner's reason.

## Quotas

Plan quotas live in code, in `PlanCatalog`, and are the documented starting point.

| Quota | Free | Personal | Business | Checked |
|---|---|---|---|---|
| Open requests (draft, issued, in progress) | 0 | 25 | not capped | at creation, against the live plan, under the owner's subscription row lock |
| Acting parties per request | 0 | 10 | 100 | frozen into the grant at issuance; each assignment reserves a place |
| Evidence files per request | 0 | 100 | 200 | frozen into the grant; checked at upload, beneath the platform ceiling |
| Evidence bytes per request | 0 | 250 MiB | 500 MiB | as above |
| Committed evidence per owner | 0 | 5 GiB | 100 GiB | at issuance. Open requests count their allowance, finished requests what they store, disposed requests nothing |

An issued request keeps its allowances whatever later happens to the plan. Retention is set by the
owner's retention schedule and no plan shortens it. Record exports are limited by a daily ceiling
that does not depend on the plan (see below), so permitted exports stay available after a lapse.

## Abuse controls

Every refusal logs `INFORMATION_REQUEST_ABUSE_REFUSED control=<control>`:

| Control                                          | Answer                                                                                                                                                                                                                                                                                                                          |
|--------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `NO_AUTH_CHALLENGE_RATE`, `NO_AUTH_SESSION_RATE` | `429` with `INFORMATION_REQUEST_RATE_LIMITED`, before any code is sent or checked. The limiter applies progressive backoff to repeat offenders: an address is paused for 60 seconds after its first two violations within 24 hours, then 300, 900 and 3600 seconds. `Retry-After` states the seconds left on the current pause. |
| `REMINDER_COOLDOWN`                              | The request is skipped in the reminder result with `cooldownUntil`, and nothing is sent.                                                                                                                                                                                                                                        |
| `EXPORT_DAILY_CEILING`                           | `429` with `Retry-After` and `INFORMATION_REQUEST_EXPORT_LIMIT_REACHED`.                                                                                                                                                                                                                                                        |
| `EVIDENCE_UPLOAD_LIMIT`                          | `413 INFORMATION_REQUEST_EVIDENCE_UPLOAD_LIMIT_EXCEEDED` when the declared size is over the file limit plus 64 KiB, before the body is read (the marker names the surface and declared bytes); otherwise `409` with the same reason.                                                                                            |
| `CONTACT_CODE_CHALLENGE_LIMIT`                   | `409 INFORMATION_REQUEST_CONTACT_PROOF_CHALLENGE_LIMIT`: an access link has sent three codes since its last successful verification, or an access session has five unanswered step-up codes. The marker names `link=<id>` or `session=<id>`.                                                                                    |
| `CONTACT_CODE_LOCKOUT`                           | `409 INFORMATION_REQUEST_CONTACT_PROOF_LOCKED` while five invalid codes have locked verification on a link or session; the marker is also logged once, with `started`, when the lockout begins.                                                                                                                                 |
| `ACCESS_LINK_USE_LIMIT`                          | `409 INFORMATION_REQUEST_ACCESS_LINK_EXHAUSTED`: the link has been used for all its verifications.                                                                                                                                                                                                                              |

Contact-code attempts are limited per link and per access session: five invalid codes lock
verification for five minutes, a link sends at most three codes before one is verified (each
successful verification lets it send three more, so the link's 25 verifications can all be used),
and a session holds at most five unanswered step-up codes.

## Evidence inspection

Each uploaded PDF is read in the application process under fixed limits. A PDF counts as
unreadable, and is kept but never satisfies a Requirement, when reading it would decode more than
16 MiB of stream content, or its cross-reference data holds more than 500,000 entries, more than
10,000 sections, or more than 1,000,000 objects in object streams. Image filters are not decoded
during PDF inspection. All file types share at most two simultaneous inspections across the process;
further uploads wait their turn before the Exchange and request are locked. Progressive JPEGs over
25 million pixels are unreadable; other supported images remain limited to 100 million pixels.

Residual risks: the PDF library still allocates in proportion to the file it parses, so a single
25 MiB file built to be repaired can use around 200 MB of heap while it is inspected, within the
two-inspection allowance of the default 1,075 MB heap. The library's shared name cache keeps names
it has seen for the life of the process. Document thumbnails are generated outside these limits.
Moving inspection into a separate process is the next step if those margins become tight.

## Workers

The clock, notice, connector, evidence scan, disposal, document version storage cleanup, and health
workers are Quarkus scheduled jobs in the application service. Each resumes from the database after
a restart. The health check logs `INFORMATION_REQUEST_HEALTH_BREACH` markers, which drive
`InformationRequestHealthBreachAlarm`.

The clock and notice workers apply the same continuation rule as a person sending a reminder. While
the owner is operationally suspended, or a request without a grant belongs to an owner whose plan
refuses changes, a due clock point records nothing and its clock is checked again an hour later. A
suspension does not move a due time: a deadline that passed meanwhile takes effect at the first check
after the suspension ends, with its overdue notice and, for a policy that expires the request, the
expiry; that overdue notice is still sent after the expiry, because it is owed by the due time that
expired the request. Clocks cannot be paused or extended during the suspension, so give the parties
more time before it starts or once it ends. A revoked grant, or one that does not list
`SEND_REMINDER`, holds the request's clock points for good. A notice that comes due under any of
these states, including a retry, is recorded as skipped with that reason and is not sent later. Any
other notice of a finished request is skipped as `REQUEST_FINISHED`.

The disposal worker skips the retention schedule of an owner who is operationally suspended, so no
request of that owner is claimed for scheduled disposal until the suspension is lifted; a disposal
that had already claimed a request finishes. Commercial lapse does not pause disposal.

The connector worker records each attempt it starts, each failed call it retries, each wait a
connector asks for, and how each exchange ends as an audited change of its request, attributed to
the platform service account and committed with the change itself. If that audit record cannot be
captured, the change is rolled back: an attempt that was not recorded never calls its connector, and
an outcome that was not recorded is discarded and the exchange is tried again after its five-minute
lease.

## Support diagnostics

| Question                                                                                                          | Where to look                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
|-------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Why can this person or organization not create requests?                                                          | `GET /information-request-capabilities` as that caller: `newWorkAvailable`, `newWorkUnavailableReason`, `featureIncluded`, `operationallySuspended`. The Exchange tab states the same reason.                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Why can a party not answer?                                                                                       | The response workspace's `executionStanding`. `OPERATIONALLY_SUSPENDED` or `EXECUTION_GRANT_REVOKED` stops changes. A lapse does not.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Why does a request's Manage page not offer an action?                                                             | The response workspace's `authorActions`, read as that manager, says which actions the server permits now, given the caller's authorization and the state of the request and its parent Exchange. The page also applies `executionStanding`. After the Exchange ends, is rejected, or is rescinded only `revokeFacts` stays `true`; on a deleted Exchange none does. A draft offers Supersede and the follow-up schedule like an issued request, but no follow-up request, accepted fact, or business decision until it is issued.                                                                                                             |
| Why does a request's follow-up history leave out a follow-up or the request it follows, or show no next due time? | The caller may not open that request. `GET .../successors` names a related request only to a caller who may view it, and gives `nextOccurrenceDueAt` and `everyOccurrenceCreated` only to one who may view every request its schedule has created; a superseded request's `supersededByRequestId` follows the same rule. Restoring the caller's party or Share on the other request lists it again.                                                                                                                                                                                                                                            |
| Why does an audit record or a record export leave out a follow-up or replacement request?                         | The caller may not open that request. A request's audit history shows `successorRequestId` and `supersededByRequestId` only to a caller who may view the request named and counts them in `withheldKeyCount` otherwise; the owner audit search keeps them. A record export names the replacement and the request behind a reused accepted fact only when its creator may view that request, and reading an export leaves out, and counts in `withheldRelatedRequestCount`, any the reader may not view; the stored export and its hash do not change. An export made by someone who may view the request names it.                             |
| Why was a party assignment refused?                                                                               | `INFORMATION_REQUEST_CAPACITY_EXHAUSTED` means the acting-party allowance is used up. `INFORMATION_REQUEST_TRUST_SUSPENDED` means the trusted relationship is suspended. `INFORMATION_REQUEST_PARTY_EMAIL_NOT_RECIPIENT` means an email named on an Exchange that requires sign-in is not the account of one of its recipients; add the person to the Exchange first. `INFORMATION_REQUEST_FIELD_OUTSIDE_AUDIENCE` means the role answers a Field its Schema does not mark Public and the holder, or a member of the group, is outside the request's owner; mark the Field Public in a new Schema Version or choose a holder inside the owner. |
| Why was issuing refused?                                                                                          | A `PLAN_LIMIT_REACHED` refusal naming committed evidence: the owner's open requests reserve their evidence allowance until they finish. `INFORMATION_REQUEST_FIELD_OUTSIDE_AUDIENCE` names the Requirement whose Field a party outside the owner could not answer; the same check refuses an amendment to such a Version.                                                                                                                                                                                                                                                                                                                      |
| Why was a reminder not sent?                                                                                      | The result's `cooldownUntil`: the request was reminded within the cooldown. A notice's skipped attempt names `OPERATIONALLY_SUSPENDED`, `EXECUTION_GRANT_REVOKED`, `CONTINUATION_NOT_GRANTED`, or `OWNER_CHANGES_UNAVAILABLE` when the owner or the grant stopped it; the clock then records no reminder either.                                                                                                                                                                                                                                                                                                                               |
| Why did a request not start from a platform Template?                                                             | `INFORMATION_REQUEST_TEMPLATE_VERSION_PLATFORM_COPY_REQUIRED`: copy the platform Template into the owner's Templates first.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Why did an Exchange not start from its Blueprint?                                                                 | The `409` reason names the request that could not be created: `..._RETIRED` (choose a current Template on the Blueprint), `..._OWNER_MISMATCH` (the Template belongs to a different workspace than the Exchange), or `INFORMATION_REQUEST_CAPABILITY_NOT_INSTALLED`. Nothing was created in any of these cases.                                                                                                                                                                                                                                                |
| Why did a connector exchange fail, or how often was it retried?                                                   | The request's audit history, as a holder of the operations view: `information_request.external.fail` carries the exchange's `failureCode` and `attemptCount`, `.retry` marks each failed call with the time of the next attempt (`nextAttemptAt`), and `.attempt` and `.pending` mark each call and each wait the connector asked for. `CONNECTOR_EXCHANGES_FAILED` in the health report counts recent failures.                                                                                                                                                                                                                               |
| Is anything stuck?                                                                                                | `GET /platform/information-request-health` (platform administrators; audited).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Why does the Exchange tab load slowly?                                                                            | Listing cost grows with the number of requests on one Exchange (about 60 ms per request in the volume test), because each request is authorized separately.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
